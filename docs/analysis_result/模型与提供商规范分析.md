# Pi 扩展模型与提供商架构规范分析报告

本文档针对 **Pi (pi-coding-agent)** 生态体系中的模型（Model）与提供商（Provider）机制进行全面技术剖析，旨在为构建 **中转站模型管理器（Model Provider Manager）**、多模型网关聚合及动态配置系统提供完整的协议标准、数据结构与实现规范。

---

## 一、 核心背景与架构概述

在 Pi 扩展机制中，模型与提供商的管理由 `@earendil-works/pi-ai` 与核心运行时的 `ModelRegistry` / `ModelRuntime` 负责：
- **Provider（提供商）**：定义上游服务的网络接入点（`baseUrl`）、通用鉴权（`apiKey` / `authHeader` / `oauth`）、默认通信协议（`api`）及全局兼容性策略（`compat`）。
- **Model（模型）**：挂载在特定 Provider 下的具体模型实体，包含模型真实标识（`id`）、显示名称（`name`）、多模态能力（`input`）、上下文及输出限制（`contextWindow` / `maxTokens`）、费率计算（`cost`）、采样参数（`samplingParams`）以及推理思考映射（`thinkingLevelMap`）。

---

## 二、 底层 API 通信协议全景（9 种 Wire Protocols）

Pi 内置实现了 **9 种** 标准 API 通信协议（`Api` 类型），分别对应不同的上游模型接口标准与流式解析器：

| 协议标识 (`api`) | 对应上游标准 / 厂商 | 适用场景与说明 |
| :--- | :--- | :--- |
| **`openai-completions`** | **OpenAI Chat Completions 协议** (`/v1/chat/completions`) | **最通用格式**。几乎所有中转站（OneAPI / NewAPI）、开源推理引擎（vLLM, SGLang, Ollama, llama.cpp）、聚合服务（OpenRouter, Together, DeepSeek, Qwen 等）均默认采用此格式。 |
| **`openai-responses`** | **OpenAI Responses API** (`/v1/responses`) | OpenAI 新一代结构化、Agent 工具调用原生协议。 |
| **`azure-openai-responses`** | **Azure OpenAI Responses API** | 微软 Azure 托管的 Responses 协议端点。 |
| **`openai-codex-responses`** | **OpenAI Codex Responses API** | 专用于 Codex 订阅端点。 |
| **`anthropic-messages`** | **Anthropic Messages API** (`/v1/messages`) | Claude 原生接口及原生 Anthropic 协议代理网关。 |
| **`mistral-conversations`** | **Mistral Native Streaming API** | Mistral 官方原生对话流式格式。 |
| **`google-generative-ai`** | **Google AI Studio (Gemini)** | Google AI Studio 官方 Gemini API。 |
| **`google-vertex`** | **Google Cloud Vertex AI** | GCP 企业级 Vertex AI 端点。 |
| **`bedrock-converse-stream`** | **Amazon Bedrock Converse API** | AWS Bedrock 原生流式协议。 |

> **扩展说明**：除上述 9 种外，如果接入完全私有化的非标协议，Extension 可通过 `streamSimple` 函数直接注入自定义的流式处理逻辑。

## 三、 模型与提供商的层级关系与继承覆盖机制

在配置和运行时层面，模型与提供商具备清晰的**两级继承与覆盖（Inheritance & Override）**规则：

```
Provider (全局默认配置)
  ├── baseUrl / headers / authHeader / apiKey
  ├── api (默认协议，如 openai-completions)
  ├── compat (全局兼容性参数)
  │
  └── Models (模型列表)
        ├── Model A (完全继承 Provider 配置)
        └── Model B (覆盖局部配置: 覆盖 api / baseUrl / headers / compat)
```

1. **协议覆盖**：Provider 可以配置默认的 `api: "openai-completions"`，但挂载在其下的特定模型（例如直接转发到 Claude 原生通道的模型）可显式覆盖为 `api: "anthropic-messages"`。
2. **端点覆盖**：单个模型可声明独立的 `baseUrl` 与 `headers`，将流量路由到特定代理端口或专有集群。
3. **参数合并**：
   - 兼容性配置（`compat`）：以 `Model.compat` 深度合并覆盖 `Provider.compat`。
   - 自定义请求头（`headers`）：Model 级别的 headers 与 Provider 级别合并，冲突项以 Model 为准。
   - 采样参数（`samplingParams`）：直接作为最高优先级覆盖项注入最终请求体。

## 四、 请求体结构与流式解析机制（底层绑定关系）

### 1. 协议绑定机制
请求体的数据组织格式与响应流的 SSE 解析器**直接与 `api` 字段强绑定**：
- 当 `api: "openai-completions"` 时，请求体构建为 `{ model, messages, tools, stream: true, stream_options: { include_usage: true } }`，流式响应按 `choices[0].delta` 解析。
- 当 `api: "anthropic-messages"` 时，请求体分离出 `system`，消息为 `messages`，流式响应按 `content_block_start` / `content_block_delta` 解析。

### 2. Pi 统一流式事件抽象（`AssistantMessageEventStream`）
无论底层是哪种协议，流式解析器均会将上游原始事件标准化为以下生命周期事件：

```
[stream.push(start)] ──► 初始化 AssistantMessage 状态
        │
        ├──► 文本流：[text_start] ──► [text_delta] ──► [text_end]
        │
        ├──► 思考流：[thinking_start] ──► [thinking_delta] ──► [thinking_end]
        │
        ├──► 工具流：[toolcall_start] ──► [toolcall_delta] (累加JSON) ──► [toolcall_end]
        │
[stream.push(done / error)] ──► 终态并记录 Token 用量与成本
```

## 五、 输入格式与多模态许可规范（Input Types）

在模型定义中，通过 `input` 数组指定当前模型允许接收的输入模态：

| 输入类型声明 | 说明 | 适用模型 |
| :--- | :--- | :--- |
| **`["text"]`** | 纯文本模式（默认）。 | DeepSeek-V3/R1, Qwen-Coder 等文本/代码模型 |
| **`["text", "image"]`** | 支持文本与图像混合输入。 | Claude 3.5/3.7, GPT-4o, Gemini 2.0/1.5 等视觉模型 |

### 多模态传输技术细节：
- **图片编码格式**：以 Base64 Data URL 或 `{ type: "base64", mediaType: "image/png", data: "..." }` 格式注入消息。
- **支持 MIME 类型**：`image/png`, `image/jpeg`, `image/webp`, `image/gif`。
- **文件（PDF / 源码 / 文档）**：在 Pi Agent 架构中，PDF 和代码文件由 Pi 本地工具（如 `read` 工具）预先提取为纯文本或图像切片，然后再传入模型上下文，因此模型层无需配置专门的文件输入类型。

## 六、 采样参数、计费费率、上下文与推理控制

### 1. 采样参数原样注入（`samplingParams`）
`samplingParams` 是一个自由键值对象，仅对 OpenAI 兼容系（`openai-completions`, `openai-responses` 等）生效。它会**原样（verbatim）覆盖合并**到发送给后端的请求体 JSON 根节点中，用于支持上游特有的采样控制：
```json
{
  "samplingParams": {
    "temperature": 0.7,
    "top_p": 0.95,
    "top_k": 40,
    "min_p": 0.05,
    "presence_penalty": 0.2
  }
}
```

### 2. 计费费率与阶梯定价（`cost`）
用于精确追踪和显示 Token 消耗成本（单位：美元 / 每百万 Token）：
```json
{
  "cost": {
    "input": 3.0,
    "output": 15.0,
    "cacheRead": 0.3,
    "cacheWrite": 3.75,
    "tiers": [
      {
        "inputTokensAbove": 200000,
        "input": 6.0,
        "output": 30.0,
        "cacheRead": 0.6,
        "cacheWrite": 7.5
      }
    ]
  }
}
```

### 3. 上下文与输出限制
- `contextWindow`：模型上下文窗口最大 Token 数（默认 `128000`）。当对话接近上限时，Pi 会触发自动上下文压缩（Compaction）。
- `maxTokens`：单次请求允许生成的最大输出 Token 数（默认 `16384`）。

### 4. 推理/思考级别映射（`thinkingLevelMap`）
Pi 内部定义了 7 档标准推理强度：`"off" | "minimal" | "low" | "medium" | "high" | "xhigh" | "max"`。
通过 `thinkingLevelMap` 可以精细化映射到上游后端的具体参数或屏蔽不支持的档位：
```json
{
  "reasoning": true,
  "thinkingLevelMap": {
    "off": null,           // null 表示不支持关闭思考（在 UI 中隐藏该选项）
    "minimal": null,
    "low": null,
    "medium": null,
    "high": "default",     // 传递给上游的值
    "xhigh": null,
    "max": "max"
  }
}
```

## 七、 兼容性适配矩阵（`compat` 参数全解）

针对各种中转站（OneAPI, NewAPI）及开源推理后端（vLLM, SGLang, Ollama, llama.cpp）的非标实现，Pi 提供了极为细致的 `compat` 开关：

### 1. OpenAI 系列兼容配置 (`api: "openai-completions"`)

| 兼容性字段 | 类型 | 说明与中转适配场景 |
| :--- | :--- | :--- |
| **`thinkingFormat`** | 枚举 | 指定推理/思考链传递格式：<br>• `"openai"` / `"openrouter"`: 传递 `reasoning: { effort }`<br>• `"together"`: 传递 `reasoning: { enabled: true }`<br>• `"deepseek"` / `"zai"` / `"ant-ling"`: 解析 `reasoning_content`<br>• `"qwen"`: 传递顶层 `enable_thinking: true`<br>• `"chat-template"` / `"qwen-chat-template"`: 传递 `chat_template_kwargs`<br>• `"baseten"`: 传递 `chat_template_args`<br>• `"string-thinking"`: 从正文中解析 `<think>...</think>` 标签 |
| **`maxTokensField`** | `"max_completion_tokens" | "max_tokens"` | 某些中转或旧版端点不支持 `max_completion_tokens`，可切换回 `max_tokens`。 |
| **`supportsUsageInStreaming`** | `boolean` | 是否发送 `stream_options: { include_usage: true }`（默认 `true`）。某些轻量中转站若报错 400，需设为 `false`。 |
| **`supportsDeveloperRole`** | `boolean` | 是否使用 `developer` 角色，设为 `false` 则回退为 `system` 角色。 |
| **`supportsReasoningEffort`** | `boolean` | 是否允许发送 `reasoning_effort` 字段。 |
| **`supportsFinishReason`** | `boolean` | 上游流式是否正常返回 `finish_reason`；若为 `false`，Pi 会在流结束时自动推断。 |
| **`requiresToolResultName`** | `boolean` | 工具执行结果消息（`role: "tool"`）中是否必须携带 `name` 字段。 |
| **`requiresAssistantAfterToolResult`** | `boolean` | 工具结果返回后，是否必须插入一条空的 assistant 消息以满足上游格式校验。 |
| **`requiresReasoningContentOnAssistantMessages`** | `boolean` | 在回放历史上下文中的 assistant 消息时，是否必须附带空 `reasoning_content`（针对某些 DeepSeek 严格校验网关）。 |
| **`requiresThinkingAsText`** | `boolean` | 是否强制将思考内容转换为普通文本块回放。 |
| **`thinkingTokenBudgetField`** | 字段名枚举 | 显式指定控制思考 Token 预算的字段名：`"thinking_token_budget"` (vLLM)、`"thinking_budget"` (Qwen/DashScope/SGLang)、`"thinking_budget_tokens"` (llama.cpp)。 |
| **`cacheControlFormat`** | `"anthropic"` | 允许在 OpenAI 协议的 system prompt、tools、messages 上标注 Anthropic 风格的 `cache_control` 提示词缓存标记。 |

### 2. Anthropic 系列兼容配置 (`api: "anthropic-messages"`)

| 兼容性字段 | 类型 | 说明与中转适配场景 |
| :--- | :--- | :--- |
| **`supportsEagerToolInputStreaming`** | `boolean` | 默认 `true`。若中转代理不支持 `eager_input_streaming`，设为 `false` 会自动回退使用 `fine-grained-tool-streaming-2025-05-14` Beta 请求头。 |
| **`forceAdaptiveThinking`** | `boolean` | 强制使用自适应思考格式（`thinking.type: "adaptive"` + `output_config.effort`）。 |
| **`allowEmptySignature`** | `boolean` | 某些第三方 Claude 代理返回空的思考签名，设为 `true` 允许在历史回放中带上 `signature: ""`。 |
| **`supportsLongCacheRetention`** | `boolean` | 是否支持 1 小时长缓存（`cache_control.ttl: "1h"`）。 |
| **`supportsStrictTools`** | `boolean` | 是否启用严格 JSON Schema 工具验证。 |
| **`supportsToolReferences`** | `boolean` | 是否支持原生的动态工具延迟加载引用。 |

## 八、 提供商与模型完整 Schema 定义（TypeScript 规范）

在构建模型管理器或中转站扩展时，推荐采用以下强类型数据结构：

```typescript
/** 9 种基础底层通信协议 */
export type ApiProtocol =
  | "openai-completions"
  | "openai-responses"
  | "azure-openai-responses"
  | "openai-codex-responses"
  | "anthropic-messages"
  | "mistral-conversations"
  | "google-generative-ai"
  | "google-vertex"
  | "bedrock-converse-stream";

/** Pi 7 档标准推理强度 */
export type ThinkingLevel = "off" | "minimal" | "low" | "medium" | "high" | "xhigh" | "max";

/** 支持的多模态输入格式 */
export type ModelInputType = "text" | "image";

/** 计费费率结构体 */
export interface ModelCostConfig {
  input: number;      // 输入费率（$/1M Tokens）
  output: number;     // 输出费率（$/1M Tokens）
  cacheRead: number;  // 缓存命中读取费率
  cacheWrite: number; // 缓存写入创建费率
  tiers?: Array<{
    inputTokensAbove: number;
    input: number;
    output: number;
    cacheRead: number;
    cacheWrite: number;
  }>;
}

/** 兼容性适配矩阵 */
export interface ProviderCompatibilityConfig {
  // === OpenAI 兼容性 ===
  supportsStore?: boolean;
  supportsDeveloperRole?: boolean;
  supportsReasoningEffort?: boolean;
  supportsUsageInStreaming?: boolean;
  supportsFinishReason?: boolean;
  supportsStrictMode?: boolean;
  supportsOpenAIGrammarTools?: boolean;
  maxTokensField?: "max_completion_tokens" | "max_tokens";
  requiresToolResultName?: boolean;
  requiresAssistantAfterToolResult?: boolean;
  requiresThinkingAsText?: boolean;
  requiresReasoningContentOnAssistantMessages?: boolean;
  
  thinkingFormat?:
    | "openai"
    | "openrouter"
    | "deepseek"
    | "together"
    | "baseten"
    | "zai"
    | "qwen"
    | "chat-template"
    | "qwen-chat-template"
    | "string-thinking"
    | "ant-ling";

  chatTemplateKwargs?: Record<string, any>;
  chatTemplateArgs?: Record<string, any>;
  thinkingTokenBudgetField?: "thinking_token_budget" | "thinking_budget" | "thinking_budget_tokens";
  supportsThinkingTokenBudget?: boolean;
  cacheControlFormat?: "anthropic";
  sendSessionAffinityHeaders?: boolean;

  // === Anthropic 兼容性 ===
  supportsEagerToolInputStreaming?: boolean;
  supportsLongCacheRetention?: boolean;
  supportsCacheControlOnTools?: boolean;
  forceAdaptiveThinking?: boolean;
  allowEmptySignature?: boolean;
  supportsStrictTools?: boolean;
  supportsToolReferences?: boolean;
}

/** 单个模型实体 Schema */
export interface ModelSchema {
  id: string;                                           // 模型 ID（传给上游的 model 字段）
  name?: string;                                        // 显示名称及别名匹配
  api?: ApiProtocol;                                    // 局部覆盖 API 协议
  baseUrl?: string;                                     // 局部覆盖端点 URL
  reasoning?: boolean;                                  // 是否具备推理/思考能力
  thinkingLevelMap?: Partial<Record<ThinkingLevel, string | null>>; // 思考级别映射
  input?: ModelInputType[];                             // 输入模态，如 ["text"] 或 ["text", "image"]
  contextWindow?: number;                               // 上下文 Token 限制 (默认 128000)
  maxTokens?: number;                                   // 最大输出 Token 限制 (默认 16384)
  cost?: ModelCostConfig;                               // 费率配置
  samplingParams?: Record<string, any>;                 // 注入请求体的采样参数
  headers?: Record<string, string>;                     // 专属请求头
  compat?: ProviderCompatibilityConfig;                 // 模型级兼容性覆盖
}

/** 提供商实体 Schema */
export interface ProviderSchema {
  id: string;                                           // 提供商唯一标识 (如 "my-proxy")
  name?: string;                                        // 提供商显示名称
  baseUrl: string;                                      // API 网关 Base URL
  apiKey?: string;                                      // 鉴权 Token (支持 $ENV, !cmd, 明文)
  api?: ApiProtocol;                                    // 默认通信协议 (建议 "openai-completions")
  authHeader?: boolean;                                 // 是否自动注入 Authorization: Bearer
  headers?: Record<string, string>;                     // 全局请求头 (支持网关 Trace ID 等)
  models?: ModelSchema[];                               // 挂载的模型列表
  modelOverrides?: Record<string, Partial<ModelSchema>>;// 针对内置模型的属性重写
  compat?: ProviderCompatibilityConfig;                 // 全局兼容性适配
}
```

## 九、 中转站/模型管理器（Model Provider Manager）落地实践与建议

1. **动态注册时机**：
   - 可以在 Extension 入口工厂函数中通过 `pi.registerProvider(...)` 注册（启动时生效）。
   - 也可以在运行期间随时由命令或 UI 配置流动态调用 `pi.registerProvider`，无需重启 `/reload` 即刻生效。
2. **Context Overflow 异常自动恢复**：
   - 中转站若返回自定义的超长截断错误，应在 `message_end` 钩子中将 `errorMessage` 规整为包含 `context_length_exceeded`，以便触发 Pi 的自动 Compaction 压缩与重试机制。
3. **网关 Header 与 Trace 注入**：
   - 使用 `before_provider_headers` 钩子可动态向中转站注入 `x-session-id` 等链路追踪信息。
4. **灵活利用 `samplingParams` 与 `compat`**：
   - 针对不同模型（如 DeepSeek-R1, Qwen-2.5, Claude-3.7-Sonnet）通过 `compat.thinkingFormat` 和 `thinkingLevelMap` 精确适配，确保思考链内容正确展示并隔离。
