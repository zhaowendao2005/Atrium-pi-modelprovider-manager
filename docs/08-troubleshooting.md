# 常见问题排查手册

使用各类第三方中转站时，难免会遇到网络波动、鉴权失败或参数报错。以下是我们在实际使用中总结出的高频问题与对应解法。

---

## 快速自查清单

遇到问题时，先按顺序确认以下 4 点：
1. **测试连通性**：在桌面端提供商面板点击「测试连通性」，看看基础网络和 Key 通不通。
2. **BaseURL 格式**：检查 URL 尾部是不是漏掉了 `/v1`（绝大多数中转站都需要包含 `/v1`）。
3. **刷新终端**：在桌面端改完配置后，记得到 Pi 终端敲一下 `/provider reload`。
4. **模型名称拼写**：确认填入的模型 ID 是否和中转站给的完全一致，不要有多余的前缀或后缀。

---

## 常见 HTTP 报错与解法

### 1. `401 Unauthorized`（鉴权失败）
- **如果你用的是环境变量（如 `$OPENAI_API_KEY`）**：  
  在终端中执行 `echo $OPENAI_API_KEY`。如果输出为空，说明当前终端会话根本没有读到这个环境变量。请在你的 Shell 配置文件（如 `~/.bashrc` 或系统环境变量）中持久化它。
- **如果中转站使用了特殊的 Header**：  
  某些企业或私有中转不认 `Authorization: Bearer <Key>`，而是要求自定义头部（比如 `api-key: <Key>`）。此时可以在抽屉中关闭「自动注入 Bearer Token」，并在「自定义请求头」中手动添加。

### 2. `404 Not Found` 或 `Model Not Found`
- **BaseURL 漏写版本号**：  
  比如将地址填成了 `https://api.deepseek.com`，拼接后就变成了 `https://api.deepseek.com/chat/completions`，直接 404。正确的应该是 `https://api.deepseek.com/v1`。
- **模型 ID 货不对板**：  
  有的中转站模型 ID 带有渠道特异前缀（例如 `a/gemini-3.7-flash`）。点击渠道右上角的「获取模型列表」，直接用官方返回的标准名称。

### 3. `522 / 504 Gateway Timeout`（连接超时）
- **现象**：测试卡片或请求返回包含 Cloudflare 的 522 错误页面。
- **原因**：中转站的源站服务器挂了、突发流量被熔断，或者中转站的 Cloudflare 防火墙把你的 IP 拦下了。
- **解法**：在测试工作台中打开该卡片的「指标」抽屉看网络时序。如果 TTFB（首字延迟）一直拉长直至中断，说明是中转源站无响应，建议切换备用渠道或联系中转站站长。

### 4. `400 Bad Request`（报 unrecognized field / unsupported parameter）
- **现象**：报错提示中包含 `unrecognized field: store`、`unsupported parameter: stream_options` 等字眼。
- **原因**：部分开源中转网关实现较早，不支持 OpenAI 官方规范中最新的实验性或统计字段。
- **解法**：进入该提供商或模型的编辑抽屉，展开 **「请求修复与中转补丁」**，勾选相应的字段剥离补丁，程序会在发送前自动清理这些参数。

## 上下文超长了怎么办？

在多轮长对话或读取了多个大型代码文件后，会话的总 Token 很容易逼近模型的物理上限（例如 128k）。

此时不同中转站返回的超长报错五花八门，很多简陋的客户端会直接崩掉。

我们内置了 **「自动上下文超长恢复」** 中间件（在设置中默认开启）。它会自动识别各种中转站的超长报错特征，并标准化为 Pi 认识的标准错误。收到这个信号后，Pi Agent 会在后台自动对早期的多轮对话进行无损滑动窗口压缩，保留最新的意图并自动重试，无需你手动清空会话。

---

## 桌面端改了配置，终端里怎么没变？

- **原因**：为了极致的响应速度，终端不会每秒都在后台轮询读取 SQLite 数据库。
- **解法**：在终端里敲一下 `/provider reload`，配置就会在毫秒级内完成热重载。
- **另外排查**：检查当前终端是不是开着开发环境（`PI_MODEL_MANAGER_ENV=development`）。如果是，它读的是 `dev-cache/` 目录的数据，与你桌面端的生产数据是隔离的。在终端里把该环境变量清空即可。
